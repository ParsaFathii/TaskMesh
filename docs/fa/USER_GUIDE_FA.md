# راهنمای کاربر — کنسول وب و اپ اندروید

این سند برای کسی است که TaskMesh را نصب کرده و حالا می‌خواهد واقعاً با آن کار کند: job بفرستد، صف را تماشا کند، ورکرها را چک کند و نتیجه را بردارد. راه‌اندازی را در [INSTALLATION_FA.md](INSTALLATION_FA.md) ببینید.

> ما فرض می‌کنیم کنسول روی `http://localhost:5173` (dev) یا `http://localhost:8081` (compose) در دسترس است و API روی `http://localhost:8080` بالا است.

---

## نقش شما چه چیزی می‌بیند؟

قبل از ورود به صفحه‌ها، این را بدانید چون کل تجربه به نقش وابسته است:

| | ADMIN | OPERATOR | USER |
|---|---|---|---|
| KPIها و queue laneها | کل کلاستر | کل کلاستر | فقط jobهای خودتان |
| workerها و metrics و audit لاگ | ✔ | ✔ | ✖ (پیام «نیازمند OPERATOR») |
| همه‌ی jobها و پروژه‌ها | ✔ | ✔ | فقط مال خودتان |
| cancel/retry | همه | همه | فقط jobهای خودتان |
| مدیریت کاربران | ✔ | ✖ | ✖ |

این محدودیت‌ها فقط «مخفی‌سازی UI» نیستند؛ backend خودش endpoint مربوطه را برای نقش اشتباه 403 می‌کند. UI فقط جلوی دیدن خطا را می‌گیرد.

## صفحه‌ی Login

- username و password حساب‌های seed (مثلاً `admin` / `TaskMesh!Admin`) را وارد کنید.
- خطاها inline نمایش داده می‌شوند: رمز غلط، سرور در دسترس نیست، یا ۴۲۹ (تلاش زیاد — rate limit لاگین ۱۰ بار در دقیقه است).
- بعد از موفقیت، JWT و اطلاعات کاربر در `localStorage` (کلید `taskmesh.session`) می‌ماند؛ session بعد از بازکردن دوباره‌ی مرورگر برقرار است و با انقضای token (۱۲ ساعت) دوباره login لازم می‌شود.

## صفحه‌ی Operations (خانه)

قلب کنسول است و در یک نگاه وضعیت کلاستر را می‌دهد:

- **KPI strip** بالای صفحه: تعداد jobهای موفق/ناموفق/در حال اجرا، عمق صف و … (برای USER فقط مربوط به jobهای خودش).
- **Queue laneها** (کامپوننت امضای TaskMesh): چهار lane عمودی CRITICAL / HIGH / NORMAL / LOW با شمارنده‌ی زنده‌ی عمق هر lane و chipهای job که در صف منتظرند. عمق laneها از metrics می‌آید (منبع حقیقت) و chipها از رویدادهای WebSocket زنده تازه می‌شوند.
- **Worker fleet**: کاشی‌های ورکر با حلقه‌ی وضعیت، سن heartbeat و flag «stale».
- **Event ticker** پایین صفحه: نوار متحرک آخرین رویدادهای زنده (job شروع شد، worker BUSY شد، …) که مستقیم از WebSocket می‌آید.
- LED وضعیت اتصال در نوار بالا: سبز = live، کهربایی = reconnecting (با شمارنده‌ی تلاش)، قرمز = قطع. اگر ۳۰ ثانیه فریمی نیاید، کلاینت خودش اتصال را بازسازی می‌کند.

## صفحه‌ی Projects

- جدول پروژه‌های شما (USER فقط مال خودش؛ ADMIN/OPERATOR همه) با دکمه‌ی ساخت پروژه (دیالوگ name + description).
- ورود به پروژه: جزئیات + لیست jobهای همان پروژه + ویرایش/حذف (فقط owner).
- پروژه‌ها مرز طبیعی دسترسی‌اند: job همیشه متعلق به یک پروژه و یک owner است.

## صفحه‌ی Jobs

- جدول فشرده با فیلترهای **project، status، type و priority** و صفحه‌بندی سمت سرور.
- سطرها با رویداد WebSocket زنده تازه می‌شوند و لحظه‌ی تغییر، فلش کهربایی کوتاهی می‌گیرند.
- روی هر سطر کلیک کنید تا وارد جزئیات شوید. دکمه‌ی «New job» (یا مسیر `/jobs/new`) برای ثبت job جدید.

## ساخت job (JobCreate)

- ابتدا **project** و **type** را انتخاب می‌کنید. فرم payload به‌صورت خودکار از endpoint زنده‌ی `GET /api/v1/job-types` ساخته می‌شود — یعنی فیلدهای هر type همیشه با کاتالوگ واقعی backend هم‌خوان است.
- بقیه‌ی گزینه‌ها: priority (LOW/NORMAL/HIGH/CRITICAL)، timeout (۵ تا ۳۶۰۰ ثانیه، پیش‌فرض ۱۲۰)، maxRetries (۰ تا ۱۰، پیش‌فرض ۳) و در صورت نیاز **idempotency key**.
- payload قبل از ارسال اعتبارسنجی می‌شود؛ خطای validation با پیام دقیق backend نمایش داده می‌شود.

## جزئیات job (JobDetail)

مهم‌ترین صفحه برای دیباگ:

- **Timeline**: stepper مراحل ثبت → صف → شروع → پایان با timestampهای دقیق.
- **لاگ زنده**: کنسول لاگ job که history را از REST می‌گیرد و خطوط جدید را از WebSocket (`job.log`) به‌صورت زنده می‌چسباند. فیلتر level (DEBUG/INFO/WARN/ERROR) هم دارد.
- **Attempts**: تاریخچه‌ی تلاش‌ها (شماره‌ی attempt، ورکر، outcome و خطا) — برای دیدن اینکه job روی چند ماشین پیچیده است.
- **Result**: اگر نتیجه inline باشد با JSON viewer درختی دیده می‌شود؛ اگر فایل باشد، لینک دانلود با هدر sha256. برای jobهای `image_resize` خروجی عکس واقعی است.
- **دکمه‌های Cancel و Retry**: فقط برای owner یا نقش OPERATOR/ADMIN نمایش داده می‌شوند. رفتار دقیق‌شان (فوری بودن cancel در QUEUED و تعاملی بودن در RUNNING) در [JOBS_FA.md](JOBS_FA.md) توضیح داده شده.
- اگر worker روی job فعال است، کارت ورکرِ همان job هم دیده می‌شود.

## صفحه‌ی Workers (فقط OPERATOR/ADMIN)

- کاشی/جدول همه‌ی ورکرها: وضعیت (STARTING/IDLE/BUSY/DRAINING/OFFLINE/ERROR)، سن آخرین heartbeat، job جاری و **flag stale** (heartbeat قدیمی‌تر از ۳ برابر interval).
- ورود به ورکر: حلقه‌ی وضعیت، مشخصات، job جاری و رویدادهای زنده‌ی همان ورکر.
- برای USER این مسیر باز می‌شود ولی به‌جای کرش، پیام «نیازمند نقش OPERATOR» می‌بیند.

## صفحه‌ی Metrics (فقط OPERATOR/ADMIN)

- تایل‌های آماری: تعداد job به تفکیک status، عمق صف به تفکیک priority، وضعیت ورکرها، مدت‌زمان متوسط/بیشینه‌ی jobهای موفق ۲۴ ساعت اخیر و throughput (تعداد تکمیل در ساعت).
- اعداد هر ۴۰۰ میلی‌ثانیه بعد از رویدادهای terminal تازه می‌شوند — همان‌طور که در عملیات واقعی لازم است.

## صفحه‌ی Settings

- پروفایل (`/me`)، نمایش/کپی token (برای دیباگ curl)، خروج از حساب و پنل اطلاعات سیستم.
- **تغییر رمز عبور در نسخه 0.1.0 در UI وجود ندارد** — این محدودیت عمداً مستند شده، نه پنهان.
- تم کنسول فقط **تیره** است؛ این طراحی عمدی کنسول عملیاتی است و گزینه‌ی تم روشن ندارد.

## اپ اندروید

اپ native (Kotlin + Compose) که مستقیم با REST API صحبت می‌کند — نه WebView. برای اجرای محلی:

1. backend را روی پورت 8080 بالا بیاورید.
2. build دیباگ را روی emulator نصب کنید: `./gradlew assembleDebug` (در `android/`).
3. در صفحه‌ی Login با حساب seed وارد شوید.

**نکته‌ی مهم emulator:** آدرس پیش‌فرض سرور در اپ `http://10.0.2.2:8080` است — `10.0.2.2` در emulator اندروید یعنی loopback ماشین شما. اگر روی گوشی فیزیکی تست می‌کنید، در همان صفحه‌ی Login یا بعداً در Settings آدرس را به IP شبکه‌ی محلی ماشین (مثلاً `http://192.168.x.x:8080`) تغییر دهید. build دیباگ اجازه‌ی HTTP ساده را دارد؛ build release فقط HTTPS قبول می‌کند.

بعد از ورود:

- **Jobs**: لیست jobها با filter chipهای status و project، pull-to-refresh و دکمه‌ی ساخت job جدید.
- **جزئیات job**: timeline، ورکر، payload، attemptها، ۵۰ لاگ آخر، نتیجه (inline یا فایل با SHA-256) و دکمه‌های cancel/retry.
- **Workers**: (فقط نقش OPERATOR/ADMIN — تب برای USER مخفی است) grid ورکرها با سن heartbeat و flag stale.
- **Alerts (Notifications)**: مرکز notification داخلی اپ — به‌جای سرویس push خارجی (FCM وجود ندارد؛ تصمیم آگاهانه)، اپ هر ۳۰ ثانیه jobهای شما (و برای اپراتورها، ورکرها) را poll می‌کند و تغییرات مهم را به‌صورت notification سیستم روی کانال `taskmesh_jobs` اعلام می‌کند: تمام‌شدن موفق/ناموفق job، timeout، cancel و OFFLINE شدن ورکر. dedup روی (job, status نهایی) انجام می‌شود تا رویداد تکراری notification نسازد.
- **Settings**: تغییر base URL، اطلاعات کاربر، خروج و نسخه.

محدودیت صادقانه‌ی notification: رویدادها فقط وقتی اپ باز است تشخیص داده می‌شوند (پس‌زمینه‌ی کامل نیاز به سرویس push دارد که در نقشه‌ی راه است). APK release هم unsigned است — قبل از توزیع باید با keystore خودتان امضا شود (جزئیات در [RELEASE_FA.md](RELEASE_FA.md)).

## پرسش‌های رایج کاربری

**job من مدت‌هاست در QUEUED مانده — مشکل از کجاست؟**
اول صفحه‌ی Workers را باز کنید (به نقش OPERATOR/ADMIN نیاز دارید): اگر ورکری آنلاین نیست، صف طبیعتاً حرکت نمی‌کند. اگر ورکرها IDLE هستند ولی job می‌ماند، یا اولویت job پایین و صف شلوغ است (aging کمکش می‌کند ولی فوری نیست)، یا نوع job در capabilityهای ورکرها نیست (مثلاً ورکرها را با `TASKMESH_CAPABILITIES` محدود کرده‌اید).

**progress مدت‌ها صفر مانده — همه‌چیز درست است؟**
بعضی handlerها آن‌قدر سبک‌اند (مثل `hash_sha256`) که فریم progress نمی‌بینید؛ برای jobهای سنگین مثل `cpu_benchmark` پیشرفت به‌صورت پله‌ای گزارش می‌شود. شاخص درست، وضعیت در header و لاگ‌های زنده‌ی صفحه‌ی جزئیات است.

**فرق Retry در UI با retry خودکار چیست؟**
retry خودکار فقط برای خطاهای گذرا تا سقف `max_retries` اجرا می‌شود و شمارنده‌اش بالا می‌رود؛ دکمه‌ی Retry برای jobهای پایانی (FAILED/TIMED_OUT/CANCELLED) است و شمارنده را صفر می‌کند — یعنی عملاً «از اول شروع کن».

**چرا بعضی نتیجه‌ها فایل‌اند و بعضی JSON؟**
خروجی تا ۳۲ کیلوبایت inline ذخیره می‌شود؛ بزرگ‌تر از آن فایل می‌شود (`image_resize` همیشه فایل است). هر دو از همان endpoint نتیجه خوانده می‌شوند و فایل‌ها sha256 دارند.

**در compose روی کدام آدرس باید بروم؟**
کنسول وب روی `http://localhost:8081` است (API خودش روی 8080 مستقیماً هم هست). در dev بدون Docker: `http://localhost:5173`.
