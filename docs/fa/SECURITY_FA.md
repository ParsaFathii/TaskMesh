# امنیت TaskMesh

این سند مدل امنیتی TaskMesh را صریح توصیف می‌کند: احراز هویت، مجوزها، اعتبارسنجی ورودی و زنجیره‌ی تأمین (supply chain). هدف‌گذاری نسخه‌ی 0.1.0 عملیاتی و اتکاپذیر بودن، نه «هر امکانات امنیتی ممکن» — پس هر جا چیزی نیست، همان‌جا نوشته شده است.

---

## احراز هویت و رمزنگاری

- **رمزهای عبور**: با BCrypt (cost 10) هش می‌شوند — حتی مدیر دیتابیس هم رمز خام را نمی‌بیند. حساب‌های seed توسعه هم با hash واقعی BCrypt در migration ثبت شده‌اند، نه plaintext.
- **token**: JWT با الگوریتم **HS256** و عمر **۱۲ ساعت** (43200 ثانیه). امضا با `TASKMESH_JWT_SECRET` انجام می‌شود و backend هر درخواست را validate می‌کند (امضا + انقضا).
- **خروج از اعتبار**: در نسخه‌ی 0.1.0 revoke فعال ندارد؛ تنها راه بی‌اعتبار کردن همه‌ی tokenها، تغییر `TASKMESH_JWT_SECRET` و restart است (کاربران دوباره login می‌کنند). refresh token هم وجود ندارد — عمداً ساده نگه داشته شده.
- **rate limit لاگین**: حداکثر **۱۰ تلاش در دقیقه به‌ازای هر username**. عبور از آن پاسخ 429 با کد `RATE_LIMITED` می‌دهد — هم دفاعی در برابر brute-force است و هم یعنی اگر تست می‌نویسید، تلاش‌های متوالی ناموفق را ببینید.

## ماتریس مجوزها (Authorization)

قاعده‌ی طلایی: **اعمال مجوز همیشه سمت سرور است.** UI فقط چیزی را مخفی می‌کند که backend قبلاً رد می‌کند؛ «مخفی» هرگز به معنی «محافظت» نیست.

| قابلیت | ADMIN | OPERATOR | USER |
|---|---|---|---|
| مدیریت کاربران (`/users`) | ✔ | ✖ | ✖ |
| دیدن همه‌ی پروژه‌ها و jobها | ✔ | ✔ | فقط مال خودش |
| ساخت پروژه / ثبت job | ✔ | ✔ | ✔ (برای خودش) |
| cancel / retry هر job | ✔ | ✔ | فقط jobهای خودش |
| دیدن نتیجه و لاگ job | ✔ | ✔ | owner |
| workerها (`/workers`) | ✔ | ✔ | ✖ (403) |
| metrics (`/metrics`) | ✔ | ✔ | ✖ (403) |
| لاگ audit (`/logs`) | ✔ | ✔ | ✖ (403) |

نقش‌ها enum دیتابیسی‌اند (`user_role`) و هنگام ساخت کاربر فقط ADMIN می‌تواند تعیین‌شان کند.

## لاگ audit

رخدادهای حساس به `audit_logs` می‌روند: `auth.login` (موفق و ناموفق)، `job.create`، `job.cancel`، `job.retry` و… با actor، resource و نتیجه‌ی SUCCESS/FAILURE. یعنی بعداً می‌توانید دقیقاً بگویید «کی، کِی، روی چه چیزی، چه کرد» — بدون آن‌که لاگ سطح کاربرد، جای لاگ امنیتی را بگیرد.

## اعتبارسنجی ورودی — دو لایه

payload هر job از **دو جای مستقل** رد می‌شود:

1. **لایه‌ی API (Java)**: `JobTypeCatalog` هر ۷ نوع را با schema دقیق (نوع فیلدها، حدود، فیلدهای اجباری) توصیف می‌کند و `PayloadValidator` قبل از ثبت، payload را می‌سنجد. نتیجه: job غلط اصلاً وارد صف نمی‌شود.
2. **لایه‌ی worker (Python)**: مدل‌های Pydantic **strict** با `extra=forbid` — فیلد ناشناخته و نوع اشتباه مردود است، حتی اگر از لایه‌ی اول رد شده باشد (دفاع در برابر نوشتن مستقیم در دیتابیس یا باگ backend).

خطای validation **non-retryable** است (job مستقیم FAILED می‌شود) و خطای گذرا retry می‌خورد — این تفکیک در handlerها صریح پیاده شده. حدود ورودی هم واقعی‌اند: CSV و متن تا 2MB، آرشیو تا 20MB، ابعاد عکس ۱ تا ۱۰۰۰۰، timeout بین ۵ و ۳۶۰۰ ثانیه و maxRetries بین ۰ و ۱۰ (constraintهای سطح دیتابیس هم دارند).

## محافظت path traversal

نتایج فایلی jobها مسیرهای نسبیِ مشتق از UUID job هستند. هنگام سرو نتیجه:

- مسیر به‌صورت canonical resolve می‌شود و باید داخل ریشه‌ی `results/` بماند.
- هر تلاش خروج از ریشه (مثل `../`) رد می‌شود و هر فایل خارج از همین الگوی UUID هم قابل درخواست نیست.

این مسیرها با تست‌های اختصاصی (معماری backend و worker هر دو) پوشش داده شده‌اند، چون «result endpoint» دقیقاً همان جایی است که رایج‌ترین باگ SERV فایل است.

## طراحی «بدون اجرای کد دلخواه»

شاید مهم‌ترین تصمیم امنیتی: **هیچ jobی در TaskMesh کد دلخواه اجرا نمی‌کند.** کاتالوگ دقیقاً ۷ نوع typed است و payload فقط داده است، نه برنامه. این یعنی:

- کاربری که job ثبت می‌کند، هیچ راهی برای اجرای کد روی workerهای شما ندارد — حتی با نقش ADMIN.
- attack surface ورکرها به باگِ ۷ handler محدود است، نه به یک interpreter عمومی.
- برای نوع job جدید باید کد واقعی در مخزن تغییر کند و از code review بگذرد.

اگر روزی اجرای کد دلخواه لازم شد، باید به‌عنوان یک تصمیم معماری جداگانه با sandbox واقعی طراحی شود — الان چیزی در این رابطه وجود ندارد و ادعایی هم نمی‌کنیم.

## مدیریت secretها

- همه‌ی تنظیمات حساس از **متغیرهای محیطی** می‌آیند: `TASKMESH_JWT_SECRET`، `TASKMESH_DB_PASSWORD`، … . هیچ secretای در repo، در compose فایل (به‌جز placeholder) یا در لاگ‌ها نیست.
- **هشدار JWT پیش‌فرض**: اگر `TASKMESH_JWT_SECRET` ست نشده باشد، backend با مقدار development (که در سورس است) کار می‌کند و در startup یک WARN صریح چاپ می‌کند. این فقط برای local dev قابل قبول است — در هر محیط دیگر، secret تصادفی و بلند بگذارید:

```bash
export TASKMESH_JWT_SECRET="$(openssl rand -hex 32)"
```

- کلیدهای امضای اندروید (keystore) هرگز commit نمی‌شوند — release APK دقیقاً به همین دلیل unsigned است.
- اسکن secret (gitleaks) روی کل تاریخچه‌ی git در CI اجرا می‌شود؛ اگر روزی secretای leak شود، pipeline قرمز می‌شود.

## زنجیره‌ی تأمین (Supply Chain)

| کنترل | کجاست |
|---|---|
| lockfile و نصب تکرارپذیر وب | `web/package-lock.json` + `npm ci` در CI |
| نسخه‌های pinned پایتون | `worker/pyproject.toml` + build wheel از همین نسخه‌ها |
| اسکن وابستگی‌های آسیب‌پذیر | workflow `dependency-review` روی PR + **Dependabot** (به‌روزرسانی خودکار) |
| SAST (تحلیل استاتیک) | **CodeQL** روی سه زبان: java-kotlin، python، javascript-typescript (روی push/PR + هفتگی) |
| اسکن leak | **gitleaks** روی کل تاریخچه |
| SBOM | سه CycloneDX در هر release: `sbom-backend.json`، `sbom-worker.json`، `sbom-web.json` (کنار artifactها در GitHub Release) |
| مالکیت بررسی PR | `CODEOWNERS` → هر تغییر نیازمند تأیید `@ParsaFathii` |
| تصاویر container | سه Dockerfile چندمرحله‌ای **non-root**، منتشرشده روی ghcr.io با digest قابل verify |

## سطح حمله و پورت‌ها

در طراحی شبکه این‌ها را به‌خاطر داشته باشید:

| پورت | سرویس | باید کجا باشد |
|---|---|---|
| 5433 (dev) / داخلی compose | PostgreSQL | فقط داخلی — هرگز عمومی؛ کل state سیستم آنجاست |
| 8080 | REST API + WebSocket | تنها نقطه‌ی ورود عمومی — پشت TLS قرار بگیرد |
| 9100+ | API کنترل ورکرها | فقط شبکه‌ی داخلی/عملیاتی — برای healthcheck و دیباگ |
| 5173 | سرور dev وب | فقط توسعه — در production وجود ندارد (nginx سرو می‌کند) |

## نکته‌های عملیاتی سریع

- **در deploy واقعی**: رمز دیتابیس ست کنید (compose بدون `TASKMESH_DB_PASSWORD` بالا نمی‌آید)، secret واقعی JWT بگذارید و ترافیک را پشت TLS ببرید.
- **اپ اندروید**: build debug فقط برای emulator است (اجازه‌ی cleartext HTTP برای `10.0.2.2`)؛ build release فقط HTTPS را قبول می‌کند.
- **کانال WebSocket**: token به‌صورت query param می‌رود؛ اگر reverse proxy دارید، مطمئن شوید URLها لاگ نمی‌شوند یا لاگ query را می‌پوشانند.
- CORS فقط برای originهای مجاز باز است (پیش‌فرض dev: `http://localhost:5173`؛ با `TASKMESH_CORS_ORIGINS` قابل تنظیم).

## چک‌لیست استقرار امن

قبل از اینکه TaskMesh را جایی جدی‌تر از لپ‌تاپ خودتان اجرا کنید، این هفت مورد را تیک بزنید:

1. [ ] `TASKMESH_JWT_SECRET` با مقدار تصادفیِ بلند (مثلاً `openssl rand -hex 32`) ست شده و هشدار default در لاگ startup نیست.
2. [ ] کاربر دیتابیس رمز دارد و trust auth خاموش است؛ `TASKMESH_DB_PASSWORD` فقط از env/secret manager می‌آید.
3. [ ] حساب‌های seed (`admin`/`operator`/`user`) یا حذف شده‌اند یا رمزشان عوض شده — رمزهای مستند در مخزن، در محیط واقعی معنا ندارند.
4. [ ] ترافیک API و WebSocket پشت TLS است (خود backend TLS نمی‌بندد — reverse proxy/nginx این کار را می‌کند؛ کانفیگ وب در `web/nginx.conf` الگوی خوبی است).
5. [ ] پورت کنترل ورکرها (9100+) فقط در شبکه‌ی داخلی قابل دسترسی است و API کنترل را expose نکرده‌اید.
6. [ ] دسترسی فایل سیستم `TASKMESH_STORAGE_DIR` محدود است (نتایج job ممکن است حاوی داده‌ی حساس payload باشند).
7. [ ] به‌روزرسانی‌های Dependabot را بی‌تأخیر مرور و merge می‌کنید — patchهای امنیتی dependencyها از همین مسیر می‌آیند.

## گزارش مشکل امنیتی

اگر آسیب‌پذیری‌ای پیدا کردید، لطفاً issue عمومی نسازید؛ به‌صورت خصوصی به مالک پروژه ([ParsaFathii](https://github.com/ParsaFathii)) اطلاع بدهید — از طریق private security advisory مخزن یا پروفایل GitHub — تا قبل از افشای عمومی فرصت رفع باشد.

## چیزهایی که (صادقانه) وجود ندارند

تا نسخه‌ی 0.1.0: تغییر رمز عبور از UI، فعال‌سازی/غیرفعال‌سازی کاربر، revoke token منفرد، MFA و رمزنگاری در حالت سکون (at-rest) برای نتایج فایلی پیاده نشده‌اند. نتایج حساس را با دسترسی فایل سیستم محافظت کنید.
